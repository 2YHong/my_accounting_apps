## 手动验证顺序

1. 打开原有账单，确认数据库升级后名称、金额、分类、账户仍然正确。
2. 导出 CSV 后直接导入，新增为 0；在 Excel 中只修改一条普通账单金额、另存为 .xlsx，导入预览应出现 1 条新增，确认后显示该账单。
3. 导入支付宝、微信原始 CSV 或 .xlsx。下载的 ZIP 先解压；文件有密码时先解除。检查账本、关联账户、默认分类选择、预览中的金额与名称。取消预览后不应新增账单。
4. 同一平台文件重复导入应新增为 0；导入后的账单改分类，再次导入仍应新增为 0。不同交易号即使内容相同也保留为不同账单。
5. 原始文件中的交易号应保留文本格式。Excel 将长交易号转为数字可能丢失精度，应重新使用原始文件。公式请粘贴为值。本版不读取 .xls，需另存为真正的 .xlsx。
6. 涉及退款、未知状态、错误金额和时间的记录只列为“需核对”，不导入；不计收支、关闭及未完成交易列为“跳过”。不要把导入总数视为原文件全部行数；核对报告之后再手动补记。外部分类统一落到选择的默认分类，未做自动智能分类。账户只是关联，不改变余额。
7. 首页预算按钮应有“预算”文字；记一笔顺序为收支类型 → 名称 → 金额 → 账户 → 账本 → 日期 → 分类 → 备注。收支按钮更高且不带图标，金额较小且不加粗。新建分类不再选择颜色。
8. 统计只保留月、年；顺序为收支概览 → 收支分类 → 收支趋势；无变化率、日均或最大支出。
9. 手机资产图为完整圆环，账户比例在下方，不展示金额。零余额和负余额不计入分布比例；最多五个账户和一个“其他”分区，完整余额仍在账户列表。
10. 夜间模式和主题颜色切换后应立即生效，重启后仍保存。检查首页、账单列表、记账表单、分类管理、统计、资产和设置的可读性。
11. 设置月度总预算和分类预算，检查实际支出计算；总账本按全部账本汇总。修改、删除预算后首页应刷新。关闭预算只隐藏首页预算入口和提示，保留预算数据；重新开启应恢复。超支金额和百分比允许超过 100%，进度条最多填满。

第三方账单格式按常见字段适配，尚未用用户的真实脱敏文件验证。若无法识别，提供保留表头和几行样例的脱敏文件，交易号可用同长度的虚构文本替代。

## 产品选择

- 标签管理入口移除，现有标签数据保留。
- 预算首版按月份，支持整个账本或分类，按实际支出计算；关闭预算不删除数据。现阶段不推送通知，超支直接在首页显示。下个月预算需单独设置，暂不自动复制。
- “周一为周起始日”是每周日历和周报的起点设置；既然只分析月、年，本版移除入口。
- 货币当前固定人民币。更换符号不等于汇率换算；多币种应在账单存原币种、原金额、入账人民币金额和入账汇率，资产也需币种。后续实现真实多币种后再开放选择。
- 语言当前简体中文，多语言最后接入。
- 原来的备份、缓存清理、更新和自动同步占位项存在未实现行为。本版设置移除这些占位操作，数据入口接到实际导入导出页面。CSV不是完整备份。
- 固定收支建议先做“周期模板 + 待确认记账”：工资、房租、订阅按月或年出现，用户确认实际金额与账户后记账。不要到期自动生成正式账单，避免与微信/支付宝导入重复。月末日期按当月最后一天处理；以模板ID和应记日期保证一次生成。模板可以暂停、跳过本期和修改下期，保留历史账单。本版仅规划，尚未实现。

# 原五端同步设计记录（已调整为 Android/iOS，尚未实现）

## 用户流程

Windows、iOS、Android、网页和 macOS 使用同一账号。输入邮箱 → 发送验证码 → 填写验证码 → 首次验证自动建立账号，已有账号直接登录。验证码重发倒计时、过期与失败提示、请求限流交给服务端；客户端不保存验证码，不在本地比较验证码。

未登录可本地记账。首次登录时显示本机账单数量，明确选择是否合并到账号。更换账号不自动混入上一个账号数据；登出清除会话，本地账本按账号隔离。先保存离线修改，再执行同步，不依赖网络才能记账。登录、同步失败不丢失现有账单。

## 后端候选

建议先评估 Supabase Auth（邮箱验证码）和 Postgres 数据库，用服务端行级权限隔离用户数据。官方 Flutter SDK列出 Windows、iOS、Android、Web 和 macOS支持；这只表示 SDK 支持，不表示目前应用已经支持这五个平台。中国大陆网络可达性、验证码邮件到达率和部署地点需要在选定服务前实际验证。

官方资料：
- https://supabase.com/docs/guides/auth/auth-email-passwordless
- https://supabase.com/docs/reference/dart/auth-signinwithotp
- https://pub.dev/packages/supabase_flutter
- https://supabase.com/docs/guides/database/postgres/row-level-security

本版没有创建云项目、开通邮件服务、配置密钥或上传账单。真正接入时需要确定部署地区、云项目和发送邮件配置。邮箱模板应发送验证码而非魔术链接。应用仅包含公开客户端密钥，管理密钥保留在服务器。

## 同步数据结构

所有账本、分类、资产账户、预算和账单都新增稳定 UUID；现有本机数字ID只用于本地查询。关联关系同步使用 UUID，不能直接拿不同设备的自增ID互相覆盖。每个实体包含 owner_id、created_at、server_updated_at、version、deleted_at。删除采用墓碑记录，以便其他设备能同步删除。

本地修改写入数据和待同步队列必须在同一个本地事务完成。客户端用操作UUID提交，服务端幂等处理，并以版本号检测冲突。设备只有收到服务器确认才清除队列。先推送本地修改，再按服务端游标增量拉取；实时通知只负责触发拉取，不是同步正确性的唯一依据。删除与编辑冲突和同一账单双端修改都保留冲突副本，提示用户选择，不能静默覆盖金额。

平台导入以 owner_id + 来源 + 交易号防重复。账单的 import_key 和未来同步UUID独立，不能共用 cloud_id。没有交易号时只能按账单内容判重，预览应说明限制。账户余额需先决定“手动快照 + 余额调整流水”还是“期初余额 + 账单流水计算”，本版沿用手动余额，不允许同步和导入隐式重算。

服务端对每张表设置 owner_id = 当前认证用户的行级读写权限，同时验证关联账本、分类、账户也属于同一用户。用户切换、上传失败重试、冲突和墓碑必须覆盖测试，不能只实现登录页面。

## 本地存储与平台适配

目前 DatabaseHelper 直接使用 sqflite，并未完成 Windows和网页的数据库工厂适配。后续先抽出 Repository 层，再选择覆盖五端的本地存储：例如统一迁到 Drift，或原生继续 SQLite，Windows接 FFI、网页接 Web数据库。不能仅加入云同步SDK就宣称五端已完成。

iOS/macOS 的构建和签名需要 macOS 环境。五端验证包括：离线记账、首次导入本机数据、双端编辑冲突、删除同步、账户隔离、网络恢复重试、时间与币种一致性、文件导入导出。
