# 邮箱验证与软件发信（2026-10-19）

本次没有连接或修改正式服务器，没有给真实邮箱发邮件。更新需要先配置发信邮箱，再安装接口，最后更新手机软件。

## 一次性配置 163 发信邮箱

1. 登录网页版 163 邮箱，在设置的 POP3/SMTP/IMAP 中开启 SMTP 服务并生成客户端授权码。
2. 登录 PocketBase 超级管理员后台，进入 Settings。应用的 Application URL 填 https://api.698239.xyz，确保验证链接使用公网域名。
3. 在 Mail settings 中配置：

| 项目 | 填写 |
|---|---|
| Sender name | 我的记账本 |
| Sender address | 用来发信的完整 163 邮箱 |
| SMTP enabled | 打开 |
| Host | smtp.163.com |
| Port | 465 |
| Username | 同一个完整 163 邮箱 |
| Password | 客户端授权码，不能用登录密码 |
| TLS | 打开 |
| Auth method | 先用默认 PLAIN；若服务商要求再按实际错误调整 |

点击后台测试发信，确认确实收到后再更新接口。授权码只填在后台，不要发到聊天，不要写入 APK 或源代码。发信邮件可能会在邮件服务商的系统、日志或发件存档中留存；软件不承诺能删除这些副本。

PocketBase 官方发信说明：https://pocketbase.io/docs/js-sending-emails/
163 授权码开通步骤（华为官方支持）：https://consumer.huawei.com/cn/support/content/zh-cn15872099/

## 安装接口

将交付的 accounting-mail-update 文件夹通过 FinalShell 上传到 /root，目录中应直接有 deploy-mail.sh、pb_hooks 和 pb_migrations。

在 FinalShell 终端执行一次：

```bash
bash /root/accounting-mail-update/deploy-mail.sh
```

脚本只安装新的邮件 hooks 和两项迁移；不会替换已有 accounting.js，也不会重导入账单集合。它会先停服备份完整 pb_data、hooks、migrations，并保留原文件。会短暂中断同步，请选无人同步时操作。未配置 SMTP 时，邮箱验证门槛迁移会停止并提示先配置。SMTP 配置检查只能检查设置项，不能替代实际收信测试。

新迁移增加两张内部辅助表（只存发送次数、时间和原登录规则），并在原 users.authRule 基础上增加 verified = true。现有未验证账号再次登录或刷新会话时要补验证；注册页可重发验证邮件。已保存账单和密钥不会因此删除。原登录限制会保留，不会被改成公开权限。

如果失败，脚本恢复原邮件 hooks 并尝试重启服务；已成功执行的迁移仍保留记录，不会擅自回滚整个账单数据库。终端会显示备份位置，保留输出便于定位。

## 用户看到的流程

- 注册：填写邮箱密码 → 收到验证邮件并点击链接 → 返回软件登录。
- 以后备份恢复码：输入原恢复码（本机先校验）→ 显示已验证的登录邮箱 → 明确同意 → 软件发信。
- 已验证邮箱不会为了发送恢复码再次收验证码。老账号只补一次验证。
- 发信成功只说明邮件服务已接受，需要用户检查收件箱和垃圾邮件，不保证最终投递。
- 每类邮件每账号至少间隔一分钟、24 小时最多五次；每类邮件整个实例上限一百次。SMTP 失败或超时的尝试也计数，防止反复发送。邮件服务商还有独立限额。
- 发送到当前登录邮箱，不能指定第三方收件人、自定义邮件内容，也不会自动重试。

## 隐私边界

邮件备份为单独、明确选择的功能。它会通过 HTTPS 把恢复码交给记账服务器，再通过受保护的 SMTP 发到用户的邮箱。服务器和邮件服务在这期间能接触恢复码，服务端理论上也可能据此解密它持有的密文。因此不能再把选择邮件备份的用户描述为“服务器绝不可能解密”。

本实现不在 PocketBase 数据表、发送队列、返回内容和自己的日志里保存恢复码。仍需管理员避免开启请求体记录、代理抓包或第三方调试日志。邮箱服务可能留存邮件。拒绝邮件备份仍可用纸张或密码管理器保存。

遗失原恢复码时，现有界面不能显示或重建原恢复码；有本机账单时先导出带密码的完整备份。恢复码不是账单副本，不能恢复已经从所有设备、服务器和备份中消失的数据。
